# Guia técnico para agentes de desenvolvimento

## Fontes e escopo

- Este repositório implementa o Webhook Delivery Service, terceiro projeto de portfólio. Há base Django em manage.py/config, saúde pública, cadastro/consulta de destinos no admin, registro/consulta de eventos, envio síncrono e consulta de tentativa por rotas restritas ao operador. Models, services.py, limits.py e delivery.py coordenam persistência, cotas e transporte HTTPS. Existe comando de retenção manual, com simulação por padrão. Ainda não há demonstração para visitantes, MVP verificado com receptor real ou entrega externa comprovada. Confira código, Git e publicação antes de afirmar disponibilidade.
- O README.md é a referência pública do comportamento implementado e dos comandos de execução. Planos não são funcionalidades entregues.
- GET /api/saude/ é a rota de saúde da aplicação em config/views.py: pública, sem autenticação, retorna status ok e não consulta banco nem serviços externos. Não interpretar seu sucesso como confirmação de disponibilidade do banco ou entrega de webhooks.
- Consulte docs/CONTEXTO_DESENVOLVIMENTO.md para preferências privadas e docs/ESTADO_WEBHOOK_DELIVERY.md para o estado recente, quando disponíveis. Não copie esses documentos para commits ou PRs.
- Inspecione o código e o estado do Git antes de presumir branches, testes, configuração ou publicação. Mantenha mudanças pequenas e relacionadas ao pedido.

## Direção técnica planejada

- Base atual: Python 3.14, Django 5.2, DRF 3.18 e psycopg 3.3, com dependências declaradas em requirements.txt. requirements-dev.txt inclui essas dependências e acrescenta pytest 9 e pytest-django 4; instalação conforme README.
- Dockerfile define imagem de desenvolvimento Python 3.14 com dependências de requirements-dev.txt, usuário app sem privilégios de administrador e comando padrão runserver. A pasta /app deve pertencer ao usuário app para permitir arquivos de execução, como cache do pytest; COPY --chown dos arquivos não substitui o ajuste da pasta de trabalho existente. .dockerignore exclui segredos, docs privados, .venv e arquivos gerados da construção. A imagem foi construída e Python/pip check foram verificados por Matheus; não inferir funcionamento do Django/banco por esses comandos.
- compose.yaml define api e PostgreSQL 17 local, portas publicadas no loopback e volume postgres_data preservado. api lê .env via env_file, sobrescreve POSTGRES_HOST=db, POSTGRES_PORT=5432 e POSTGRES_SSLMODE=disable, e depende de db saudável. O código fica copiado na imagem, sem bind mount; reconstruir depois de alterações. Execução conjunta, saúde HTTP e consulta às migrations pelo serviço api foram verificadas. Django na .venv continua alternativa, iniciando somente db pelo Compose. settings.py lê POSTGRES_* do ambiente e repassa sslmode ao driver, com require por padrão; disable é apenas para este banco local sem TLS, require para Neon. Não presumir serviço iniciado ou migrations aplicadas sem evidência.
- A base está publicada na Vercel Hobby em https://webhook-delivery-api.vercel.app/api/saude/; resposta 200/status ok e interface DRF estilizada foram verificadas no navegador. Logs de build confirmam seleção Python 3.14, Django 5.2.18 e execução de collectstatic com publicação concluída. Neon Free fornece o PostgreSQL hospedado, consultado e migrado pelo terminal. Em 17/10/2026, uma tentativa de login no admin publicado com dados fictícios retornou a mensagem padrão de credenciais inválidas; com o backend de autenticação padrão presente, isso verifica a consulta ao banco pela execução hospedada. Não inferir essa conexão pela saúde, nem interpretar a recusa como login autorizado ou verificação de gravação. A demonstração interativa de webhooks ainda não existe. Revalidar cotas e configuração dos planos gratuitos ao ampliar o uso.
- A demonstração deve executar requisições HTTP reais e persistir resultados, com dados fictícios e receptores controlados. Manter a interface pequena e servir a API e a interface no mesmo projeto quando possível.
- MVP proposto: cadastrar destinos autorizados e seu tipo de evento, registrar um evento para um único destino, solicitar uma tentativa síncrona e consultar estado e tentativa. Não pressupor envio automático, fila ou múltiplos destinatários.
- No envio síncrono, a API responde à solicitação de envio depois de registrar o resultado da tentativa HTTP externa. Registrar um evento não dispara o envio. Uma eventual execução em segundo plano exigirá mecanismo supervisionado e contrato de aceitação/consulta próprio.
- WebhookEndpoint tem UUID, URL, event_type, created_at e unicidade URL/tipo; admin permite cadastro/consulta com add/view, sem edição/exclusão inclusive para superusuários. Event tem UUID, endpoint PROTECT, event_type, payload, status e created_at; POST /api/eventos/ registra201/pending, GET /api/eventos/<uuid>/ consulta200/404, POST /api/eventos/<uuid>/enviar/ executa tentativa e GET /api/eventos/<uuid>/tentativa/ consulta metadados. Sem listagem/edição/exclusão HTTP ou admin de eventos/tentativas. Cadastro não inicia envio.
- Retry, assinatura HMAC e seu secret, idempotency key, Redis e Celery ficam para evolução. Não adicionar dependências ou infraestrutura apenas por aparecerem no contexto original.
- post_json(url, data) é transporte isolado: revalida destino, faz um POST HTTPS e retorna DeliveryResult com http_status/error_code, sem ORM. EventSendView chama deliver_event(event_id, initiated_by=request.user), que integra transporte, cotas, tentativa e estado. Não expor o helper diretamente nem praticar envio externo sem receptor controlado e orçamento deliberadamente habilitado.

## Convenções de implementação

- Prefira recursos do Django e do DRF. Validação de entrada no serializer, coordenação HTTP na view, persistência nos models, coordenação da entrega em services.py e transporte externo em delivery.py. Essas funções não constituem outro serviço ou adoção integral de Clean/hexagonal.
- Para destinos, webhooks/validators.py centraliza URL e formato do tipo; o admin usa a validação dos campos do modelo. save() não chama full_clean(): escritas diretas pelo ORM devem validar explicitamente. Não expor uma nova entrada sem reutilizar essas regras; a restrição de unicidade no banco não valida a segurança da URL.
- Event.clean() valida payload também quando vazio (aceita {}, rejeita listas/null), compatibilidade de tipo e autorização atual da URL do destino. validate_event_payload exige objeto JSON de até 16 KiB em JSON compacto UTF-8, com chaves de texto e valores compatíveis com JSONB; não faz HTTP/DNS. Migration 0004_event_delivery_states amplia event_valid_status para pending/sending/delivered/failed e o resultado de tentativa para incluir destination_rejected. As restrições não coordenam transições ou relação entre estado e tentativa; o serviço mantém essas regras. Eventos com conteúdo igual têm IDs distintos; não há chave de idempotência.
- EventSerializer aceita somente endpoint_id (UUID de destino existente), event_type e payload; id/status/created_at são de saída e qualquer campo extra é rejeitado. Executa full_clean() antes de permitir criação, reaproveitando as regras de negócio e mapeando erros de endpoint para endpoint_id. CreateAPIView/RetrieveAPIView atendem HTTP; JSONParser restringe o corpo de cadastro a application/json. Não deduzir segurança de envio externo dessas validações.
- DeliveryAttempt usa UUID, event OneToOne/PROTECT, started_at, finished_at opcional, http_status opcional200–599 e error_code vazio/http_error/network_error/timeout/destination_rejected. Migration0003 cria a tabela,0004 amplia resultados,0005_delivery_access adiciona initiated_by FK opcional para AUTH_USER_MODEL/SET_NULL e permissão Event.send_event. Histórico pode ter autoria nula; autoria de novas chamadas HTTP vem de request.user, nunca do corpo. Validação/banco exigem término>=início e resultado coerente: sem término não há resultado; HTTP2xx não tem erro; HTTP3xx–5xx exige http_error; concluída sem HTTP exige network_error/timeout/destination_rejected. Não guardar corpo/headers externos ou texto bruto de exceções. Modelo gera só permissão view; serializer de leitura expõe id,event_id,event_status,started_at,finished_at,http_status,error_code, sem payload/URL/operador. OneToOne não substitui coordenação ou permite recuperação automática.
- deliver_event(event_id, initiated_by=None) usa _start_delivery: revalida evento/URL sem DNS, muda condicionalmente pending para sending, confere cotas e cria tentativa na mesma atomic(durable=True). Falha antes do commit reverte início; concorrente/repetição recebe DeliveryAlreadyStarted. Monta envelope id UUIDtexto,event_type,created_at ISO8601,payload e chama post_json fora de transação; outra transação durável valida/grava resultado e estado delivered(HTTP2xx)/failed. Não chamar dentro de outra transação comum. InvalidEventForDelivery preserva ValidationError do full_clean inicial; erros internos de envelope/finalização não devem ser tratados como entrada400. Rejeição do transporte após início vira destination_rejected; interrupção/falha inesperada ou falha na gravação final pode deixar sending/tentativa incompleta, bloqueando novo início. Não inventar resultado nem recuperar automaticamente; persistir resposta observada mesmo se allowlist mudar depois.
- limits.py verifica janela móvel60s por initiated_by e24h global por started_at, contando falhas/incompletos/autoria nula; chamadas sem operador compartilham grupoNULL. WEBHOOK_MAX_DELIVERIES_PER_MINUTE default3 e WEBHOOK_MAX_DELIVERIES_PER_DAY default0: qualquer zero desabilita; exigir inteiros>=0. check_delivery_limits executa na transação de início, com pg_advisory_xact_lock e lock_timeout1s; lock liberado antes da rede. DeliveryLimitError identifica disabled/busy/global_limit/operator_limit e retry_after calculado; limites não são proteção DDoS. Retenção não pode apagar tentativas recentes e reduzir a contagem da janela.
- purge_webhook_data é comando manual: sem flags apenas simula; --apply exclui pendentes sem tentativa e concluídos delivered/failed com datas de evento/início/término estritamente anteriores a7dias. Preserva incompletos/recentes/usuários/destinos. Lotes100 em atomic durável; trava Event com skip_locked, revalida elegibilidade, exclui tentativa antes do evento por PROTECT. Falha desfaz só lote atual; anteriores permanecem confirmados. Registros ocupados ficam para outra execução. Sem cron ou limpeza automática; conferir simulação/banco-alvo antes de exclusão e autorização aplicável para dados hospedados.
- delivery.py usa cliente/parser HTTP e TLS da biblioteca padrão. ResolvedDestination/DeliveryResult são dataclasses em memória, não models. O chamador valida negócio e monta o JSON; post_json limita o corpo compacto UTF-8 a 17 KiB (não muda o limite de 16 KiB do payload na API). ValidationError rejeita corpo/URL/política de IP; falhas de transporte retornam metadados sem detalhes internos. HTTP 200–299 retorna erro vazio, 300–599 http_error; sem HTTP, timeout ou network_error. Não aceitar parâmetros de método/headers nem copiar cookies/credenciais recebidos. Não retornar corpo/headers externos nem detalhes brutos de exceções.
- Use comandos oficiais para estruturas padrão e migrations. Gere migrations quando o esquema mudar e revise antes de aplicar.
- STATIC_URL é /static/ e STATIC_ROOT aponta para staticfiles/ na raiz, pasta gerada e ignorada pelo Git. Verificar coleta com manage.py collectstatic --noinput. A Vercel coleta automaticamente quando STATIC_ROOT está definido; verificar entrega HTTP dos arquivos após deploy, sem presumir sucesso pela coleta local.
- Use inglês claro nos identificadores Python, aspas simples por padrão e português nas mensagens ao usuário e na documentação. Preserve nomes exigidos pelo framework e contratos já publicados.
- Não acrescente comentários explicativos ou docstrings manuais ao código e aos exemplos de configuração. Preserve os comentários/docstrings originais de arquivos gerados pelo Django ou por outras ferramentas. Mantenha as explicações no README e na comunicação de revisão.
- Atualize o README quando o contrato HTTP, a configuração ou a execução real mudar. Não documente planos como comportamento disponível.

## Segurança e dados locais

- Desenvolver localmente e preparar uma demonstração pública restrita, com dados fictícios e destinos previamente autorizados pelo operador. Não apresentar a demonstração como serviço de envio para URLs arbitrárias ou plataforma multiusuário de produção.
- Antes de expor operações de cadastro ou envio na demonstração, restringir a administração dos destinos, definir acesso, limites de requisições, orçamento global de envios e retenção de dados. O visitante só pode usar receptores controlados; proteger essas regras no backend, não apenas na interface. A saúde pública já publicada não habilita essas operações.
- URLs fornecidas por usuários podem causar SSRF: acesso indevido à máquina, à rede interna ou a metadados de nuvem. Validar sintaxe não basta.
- WEBHOOK_ALLOWED_URLS é uma lista de URLs completas exatas, separadas por vírgulas, fornecida pelo ambiente; vazia bloqueia novos cadastros. Validação exige HTTPS/443, sem credenciais/query/fragmento, e rejeita nomes locais/internos conhecidos e IPs literais não públicos. Cadastro não faz HTTP/DNS; domínio permitido ainda pode resolver para IP interno, portanto não descrever essas regras como proteção completa de envio. Revalidar a configuração/destino antes de futuro despacho, mesmo para registros antigos. Nenhum segredo de assinatura foi criado.
- O transporte interno revalida allowlist e todos os IPs retornados pelo resolvedor; mistura público/privado bloqueia o destino. Exige global sem multicast/reservados; IPv6 somente 2000::/3 nativo, sem scope/mapped/6to4/Teredo/NAT64. Normaliza IDNA/caminho e rejeita domínio não convertível. A conexão usa diretamente um IP validado (IPv4 preferido), mantendo hostname original em TLS/SNI com certificado obrigatório; sem nova resolução, proxy do ambiente, redirects ou retry. Não chamar uma validação de DNS isolada de proteção completa.
- TCP/TLS compartilham 3 s; escrita tem 5 s/operação; leitor da resposta aplica prazo de 5 s e cota de 16 KiB usando parser HTTP padrão. Corpo não é consumido integralmente, mas buffer pode antecipar bytes dentro da cota. DNS usa resolvedor do sistema sem prazo próprio: não prometer timeout global DNS+envio nem improvisar threads soltas para cancelá-lo. Fechar recursos também em erro/interrupção. Rota de envio restrita ao operador tem cotas e permanece desabilitada por padrão; abertura a visitantes exige escopo/configuração/verificação próprios.
- Não aceitar método ou headers arbitrários do usuário, encaminhar credenciais recebidas nem desabilitar a verificação TLS. Falhas externas devem ser registradas sem expor segredos ou detalhes internos.
- Persistir a tentativa antes da chamada externa e seu resultado depois. Evitar transação de banco aberta durante a chamada; impedir duas solicitações concorrentes de iniciar o mesmo evento.
- Timeout não prova que o destinatário deixou de receber o evento. Não prometer entrega exatamente uma vez nem recuperar automaticamente envios de resultado incerto.
- Mantenha docs/, .env, variantes locais de .env e .venv/ fora do versionamento. .env.example deve conter somente exemplos sem segredos.
- DJANGO_SECURE_COOKIES controla SESSION_COOKIE_SECURE e CSRF_COOKIE_SECURE, independentemente de DEBUG: ativados por padrão, desativados somente pelo texto exato False. .env.example indica False apenas para desenvolvimento local por HTTP; na hospedagem HTTPS usar True ou omitir a variável. PR #3 publicada, saúde/admin 200 e cookie CSRF com Secure observados por Matheus. Cookie de sessão ainda não observado em acesso autenticado; não declarar ambos verificados por ver apenas csrftoken.
- Na Vercel atual, HSTS e redirecionamento HTTP para HTTPS são responsabilidade da plataforma: verificados no Bruno por Strict-Transport-Security e 308/Location. Não adicionar SECURE_SSL_REDIRECT, HSTS ou confiança em headers de proxy apenas para zerar W004/W008 do check --deploy local; esse comando não inspeciona a plataforma. Não silenciar esses avisos indiscriminadamente; reavaliar a decisão ao trocar de hospedagem.
- A configuração lê DJANGO_SECRET_KEY, DJANGO_DEBUG e DJANGO_ALLOWED_HOSTS do ambiente. DEBUG só é ativado pelo texto exato True e fica desativado por padrão; ALLOWED_HOSTS é uma lista separada por vírgulas, vazia por padrão. O .env.example indica True e hosts locais para desenvolvimento. Na publicação, usar False e domínios específicos, sem wildcard; essa lista não autoriza destinos externos de webhooks. O Django não lê .env automaticamente: na .venv, carregue-o no terminal conforme o README; no container, o Compose fornece os valores. Revisão de segurança acompanha cada operação, incluindo cookie de sessão antes de uso autenticado. O DRF não possui política global explícita de permissões neste projeto; definir acesso dos novos endpoints antes de expô-los, sem presumir autenticação por ter o framework instalado.
- Rotas de eventos usam explicitamente SessionAuthentication, IsAdminUser e EventModelPermissions: usuário ativo da equipe e add_event no POST, view_event no GET/HEAD/OPTIONS. POST autenticado exige CSRF; falta de sessão/permissão ou CSRF retorna 403. Permissões são por modelo, sem isolamento por proprietário; manter operações internas ao operador até a demonstração restrita possuir controles próprios. Não habilitar Basic/token/JWT ou abrir cadastro anônimo por conveniência de teste. Saúde continua pública e sem autenticação.
- Consulta de tentativa usa SessionAuthentication/IsAdminUser/CanViewDeliveryAttempt(view_deliveryattempt), busca por event_id e retorna404 sem tentativa; GET/HEAD/OPTIONS somente leitura. EventSendView usa sessão/staffativo/CanSendEvent(send_event), JSONParser e DeliveryRequestSerializer: corpo vazio/{} apenas. POST exige CSRF, usa dados persistidos e request.user. Resposta200 significa resultado registrado, inclusive http_status500 externo ou timeout/failed. Entrada400/415, falta de acesso/CSRF403, ausente404, repetição409, cota429, disabled/busy503 com Retry-After quando há espera definida. Falha interna500JSON genérico e log apenas da classe, sem mensagem bruta. Send não concede consulta de histórico; não presumir isolamento por proprietário.

## Verificação

- pytest.ini define config.settings e descoberta de test_*.py. O comando é python -m pytest -q (ou docker compose exec api python -m pytest -q). Saúde/validações isoladas não usam banco; testes de persistência/admin/API de eventos e de tentativas usam pytest-django com PostgreSQL local em banco separado. A maioria dos testes de autorização usa force_login; um teste de eventos exercita login com senha, sessão/CSRF e cookies Secure via HTTPS simulado no cliente Django. Nenhum desses testes comprova conta ou cookies autenticados na hospedagem. Não presumir execução ou aprovação sem evidência; nenhum teste encontrado (código 5) não significa aprovação.
- Acrescente testes de comportamento a cada parte: sucesso, entradas inválidas, recurso inexistente, efeitos no banco, repetição e concorrência no envio, falhas HTTP/rede e restrições de destino.
- Testes automatizados devem simular HTTP externo e DNS, sem depender de serviços públicos nem enviar dados reais. Testes de concorrência devem usar transações reais do PostgreSQL quando necessário.
- tests/test_delivery_destination.py e tests/test_delivery_http.py não usam banco nem rede externa. O segundo usa parser HTTP real com sockets/TLS simulados; verifica argumentos/configuração TLS e exceções, não handshake ou entrega contra receptor real. Não inferir envio real por esses testes nem habilitar envio automático no cadastro para facilitar uma verificação manual.
- tests/test_delivery_service.py usa transações reais locais e transporte simulado para início, envelope, resultados, repetição e falhas. tests/test_delivery_concurrency.py sincroniza dois concorrentes em conexões PostgreSQL distintas, verificando uma tentativa e uma chamada ao transporte no cenário de envio. Threads existem somente no teste; não há worker/fila ou execução assíncrona na aplicação. Não executar a suíte contra Neon.
- tests/test_delivery_limits.py cobre cotas/janelas/configuração/lock limitado; test_delivery_attempt_api.py e test_delivery_send_api.py cobrem HTTP/permissões/CSRF/erros/conflitos, com envio simulado. test_delivery_retention.py exerce simulação/exclusão por lote, rollback, cotas preservadas e concorrência com envio. Exclusões desses testes ocorrem apenas no banco separado de testes; não executar --apply em dados reais por conveniência de verificação.
- manage.py check e verificações de migrations complementam os testes de comportamento.
- Use Bruno API Client para testes manuais, registrando método, URL, autenticação, JSON, status, resposta e efeitos observados.
- Diferencie verificações próprias de resultados relatados pelo usuário. Não declare testes, commits ou operações executadas sem evidência.

## Git e entrega

- main é a branch principal. Faça um primeiro commit de base cedo; depois use branches de trabalho, commits por partes lógicas revisadas e verificadas e PR antes do merge.
- Use português nos nomes de branches e mensagens de commit; prefixos como feat, fix, test, docs e chore podem permanecer em inglês.
- Confira os arquivos preparados antes de cada commit, preserve os arquivos privados e faça push antes da PR. Descreva na PR somente alterações e verificações efetivas.
- Não execute commit, push, merge ou publicação sem autorização aplicável. Respeite a divisão de trabalho combinada com o usuário para comandos e edição de código.
- Analise divergências ou conflitos antes de atualizar branches. Não presuma que o remoto está vazio ou vinculado sem conferir.
